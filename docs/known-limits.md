# Known limits

After `new` / `preview` work, read these bounds. They are the CLI and kernel as they ship. A green test, a working example, or exit code 0 from `validate-atlas`, `direction validate`, `project validate`, or the game-pack check still sits inside them.

装好并跑通 `new` / `preview` 之后，先看这些边界。测试通过、示例能跑、校验退出码是 0，仍然落在这些边界里。

## Same-project edits wait; they are not merged

会改同一份工程、图块地图或清单的命令，在读取要当作编辑依据的内容之前，先取得该路径的跨进程排他锁，并一直持有到这次命令结束。锁文件是规范化路径旁边的 `<文件名>.pixelforge.lock`。实现用的是 `fs4` 的 `flock(2)`（Unix）和 `LockFileEx`（Windows）。进程被杀掉时由操作系统放开这把锁。命令结束只解锁、关句柄，不删除锁文件：删除后，正在等的进程仍占着旧 inode，新进程会在同名路径上新建另一份文件，两把锁就不再互斥。不同路径互不阻塞。这不是后台队列，也不保证先来先服务。

默认最多等 30000 毫秒。`PIXELFORGE_LOCK_TIMEOUT_MS` 可以改成别的毫秒数，`0` 表示试一次。超时的 stdout 只有一行 `error.code` 为 `LockTimeout` 的 JSON，退出码 2，进程没有读取、也没有改写工程。`inspect`、`scene`、`preview`、`diff`、`export`，以及一批里全部是只读工具的 `call`，不取这把排他锁。只读命令看到的是替换之前或之后的完整文件。

指向已经存在的文件的符号链接，和真实路径用同一把锁，写入落在规范化后的目标上。悬空符号链接，以及锁文件本身是符号链接，都是 `UnsupportedPath`，退出码 2，不改工程。硬链接（链接数大于 1）同样拒绝：锁身份是路径，盖不住同一个 inode 的另一个名字。编辑过程中若有人从外面再做硬链接，这一次检查发现不了。

保存是同目录里的唯一临时文件：写完、在 Unix 上尽量沿用原文件的权限位、`sync_all`，再改名替换。替换前失败会删掉临时文件，原路径的字节不动。进程在替换前退出时，原文件还在；可能留下 `.<名字>.<pid>.<纳秒>.<序号>.tmp`，那不是工程，确认没有 `pixelforge` 正在写它之后可以删。Unix 在改名后再同步父目录；文件系统返回 `EINVAL`、`ENOTSUP` 或 `ENOSYS` 时，保存仍然成功，因为新内容已经可见，但这次不声称目录项能扛掉断电。其它目录同步错误是 `DirectorySync`：新内容已经在原路径上。Windows 不复制原来的 ACL，也不做目录同步；成功只表示读者会看到一份完整的旧文件或一份完整的新文件。网络盘、云同步目录，以及不经过这把锁直接写 JSON 的程序，都不在这个保证里。

工程文件和 `--checkpoint` 是两次替换。工程已经写下、检查点还没写下时进程失败，工程保留这次编辑，检查点仍是旧的；下一次带这个检查点的命令得到 `CheckpointMismatch`，不会把工程改回去。这不是一次事务。一批请求仍是「失败前的编辑保存，失败后的不再执行」，锁超时发生在任何一个请求之前，所以这一批不会留下半截。可选的内容指纹见下一节。

*A command that can change a project, tilemap, or manifest takes an exclusive cross-process lock before it reads the bytes it will edit, and holds that lock until the command finishes. The sidecar is `<filename>.pixelforge.lock` beside the canonical path. The primitive is `fs4`: `flock(2)` on Unix and `LockFileEx` on Windows. The OS releases it when the process dies. The command unlocks and closes the handle; it does not delete the sidecar. Deleting the sidecar lets a waiter keep the old inode while a new process creates another file at the same name. Different paths do not block each other. The wait is not a queue and is not first-in-first-out.*

*The default bound is 30000 milliseconds. `PIXELFORGE_LOCK_TIMEOUT_MS` changes it; `0` tries once. A timeout prints one JSON line with `error.code` `LockTimeout`, exits 2, and does not read or change the project. `inspect`, `scene`, `preview`, `diff`, `export`, and a `call` whose tools are all read-only do not take this exclusive lock. A reader sees one complete old file or one complete new file.*

*A symlink to an existing file shares the lock with the real path, and the write lands on the canonical target. A dangling symlink, or a lock sidecar that is itself a symlink, is `UnsupportedPath`, exit 2, and does not change the project. A hard link (link count above 1) is refused for the same reason: the lock identity is the path, so a second name for the inode is not covered. A hard link added from outside during the edit is not detected.*

*The save writes a unique temp file in the same directory, copies the existing Unix mode bits when the file is already there, calls `sync_all`, and renames it into place. A failure before the rename removes the temp and leaves the original bytes. A crash before the rename leaves the original file and may leave `.<name>.<pid>.<nanos>.<salt>.tmp`; that file is not the project, and it can be removed once no `pixelforge` process is writing it. After the rename, Unix syncs the parent directory. `EINVAL`, `ENOTSUP`, and `ENOSYS` still count as a successful save, because the new bytes are already visible, and that save does not claim the directory entry survives power loss. Any other directory-sync error is `DirectorySync`: the new contents are already at the original path. Windows does not copy the previous ACL and does not sync the directory. Success means a reader sees one complete old file or one complete new file. Network drives, cloud-sync folders, and a program that writes the JSON without this lock are outside this guarantee.*

*The project file and `--checkpoint` are two replacements. If the process fails after the project write and before the checkpoint write, the project keeps the edit and the checkpoint stays old. The next command with that checkpoint returns `CheckpointMismatch` and does not roll the project back. That is not one transaction. A batch is still "save the edits that ran, stop at the first refusal". A lock timeout happens before any request, so that batch does not leave a prefix.*

## 过期视图要自己带指纹

`scene` 和 `inspect` 的 `result.revision` 是刚读入的那份规范化工程文本的 FNV-1a 64，16 位小写十六进制。顶层 `revision` 是同一个值。它不写入工程，也不靠 mtime 或文件大小。只读和无变化编辑不会变成另一个指纹。编辑命令可以带 `--expected-revision`。锁拿到并读完当前文本之后、任何工具和保存之前核对一次。不一致是 `RevisionConflict`（退出码 2），stdout 只有这一条错误，带 `expected`、`current` 和重新读取的提示，工程和检查点都不写。格式不对是 `RevisionInvalid`。`new`、`import-aseprite --output`、`convert --output` 没有可对照的旧快照，带上这个参数是 `RevisionUnsupported`，不创建文件。

不传这个参数时，行为和第一阶段一样：有锁和原子替换，不检查调用方是不是拿着旧视图。一批请求只在开头核对一次；失败前的编辑仍会保存。`tilemap` 和 `asset` 子命令不接受这个参数，传入会被 clap 拒绝。要对地图或清单做同样的检查，用 `pixelforge call --project FILE --expected-revision`。冲突后重新 `scene`，按新画面重做计划，不要重放旧命令。

*The `result.revision` on `scene` and `inspect` is the FNV-1a 64 of the canonical project text just loaded, 16 lowercase hex digits. The top-level `revision` is the same value. It is not stored in the project, and it is not the mtime or the file size. A read-only command or an edit that changes nothing keeps that fingerprint. An edit may pass `--expected-revision`. The check runs after the lock is held and the current text is read, once, before any tool or save. A mismatch is `RevisionConflict` (exit 2): one error line, with `expected`, `current`, and a hint to read again. The project and the checkpoint are not written. A malformed token is `RevisionInvalid`. `new`, `import-aseprite --output`, and `convert --output` have no snapshot to match, so the flag is `RevisionUnsupported` and creates nothing.*

*Omit the flag and phase 1 remains: the lock and the atomic save, without a stale-view check. A batch is checked once at the start; edits before a later refusal are still saved. `tilemap` and `asset` subcommands do not accept the flag; clap rejects it. Use `pixelforge call --project FILE --expected-revision` for a map or a manifest. After a conflict, run `scene` again and plan from the new picture. Do not replay the old command.*

## Unbound polish stays on canvas cells

绑定到部件的 `polish` 层按部件局部坐标理解：本地 `(0, 0)` 是部件原点，或 `layer bind --anchor` 点名的锚点。`bake` 以及 `part translate` / `rotate` / `flip` 会把这一层的修正连同显式擦除一起搬走。没绑定的覆盖层仍是 [#72](https://github.com/starcloud530/pixelforge-ai/issues/72) 的行为：`bake` 不写它，格子留在画下的那一格。显式擦除是覆盖层上的透明格，和「这一格没改过」不是一回事；`erase-rect --unmodified`（Tool API `mode: pass`）才清回未修改。曲线或约束管着的生成层仍从源帧整层重建，修正不要画在那一层上。旋转补洞仍然有损，绑在部件上的精修跟着转时一样。一层只绑一个部件。见 [#99](https://github.com/starcloud530/pixelforge-ai/issues/99)。烘焙命令见 [agent-skill](agent-skill.md)。

*An unbound `polish` overlay stays on the canvas cell where it was painted. That is still the [#72](https://github.com/starcloud530/pixelforge-ai/issues/72) behavior: `bake` does not write it. A polish layer bound to a part stores the correction in that part's local frame. Local `(0, 0)` is the part origin, or the anchor named by `layer bind --anchor`. `bake` and `part translate` / `rotate` / `flip` move those cells, including an explicit erase. An explicit erase is a transparent overlay cell, distinct from a cell that was never touched. `erase-rect --unmodified` (Tool API `mode: pass`) clears it back to pass-through. A layer a curve or constraint manages is still rebuilt from the source frame, so the fix does not belong on that generated layer. Rotation sealing stays lossy when the bound overlay turns with the part. One polish layer binds to one part. See [#99](https://github.com/starcloud530/pixelforge-ai/issues/99). Bake commands: [agent-skill](agent-skill.md).*

## Rotation sealing is lossy

非直角旋转在最近邻之后做覆盖补洞。缺口比只做正向映射少，质量有改进，仍然有损。`dropped` 不会因为补上格子变成 0。单像素细线仍可能断开（`breaks` 大于 0），靠近 45° 时还会变短。墨水数量回到源格数不等于修好。见 [#73](https://github.com/starcloud530/pixelforge-ai/issues/73)。旋转不能代替手修。

*Rotation past a right angle is nearest-neighbor rasterization plus a coverage seal. The seal closes more notches than forward mapping alone. Quality is better, and it is still lossy. Sealing does not clear `dropped`. A one-pixel line can still break (`breaks` above 0) or shorten near 45°. Ink count matching the source is not a finished edge. See [#73](https://github.com/starcloud530/pixelforge-ai/issues/73). Rotation does not replace a hand pass.*

## IK places joints; it does not author gait

短链是 2 或 3 节，加上 `pin` 和 `plant` 把脚钉在接触点上。它不自动编写自然步态，也不从一条静止姿势生成走路循环。没有整棵 IK 树，没有步态生成器，也没有物理。见 [#68](https://github.com/starcloud530/pixelforge-ai/issues/68)。an external driver script (kept out of this repo; see companion demos when published) 钉的是接触帧。走路帧仍要自己关键帧，或同姿复制后改差，再 `bake`。

*Short-chain IK is two or three parts. `pin` and `plant` hold a foot on a contact. The solve places joints. It does not author a natural gait, and it does not turn one rest pose into a walk cycle. There is no full IK tree, no gait generator, and no physics. See [#68](https://github.com/starcloud530/pixelforge-ai/issues/68). an external driver script (kept out of this repo; see companion demos when published) plants contact frames. Walk frames are still keyed, or duplicated and edited, then baked.*

## Translucent flatten snaps to nearest index

彩色 preview、`export png` 和 `frame_rgba` 仍是直通 alpha 的 RGB 混合，不改格子。ASCII 和 `diff` 在压平之前仍是盖住的索引。`layer flatten` 把这一张混合按 `apply-png` 的规则收成调色板索引：alpha 小于 128 写成索引 0，否则按平方 RGB 距离取最近的非 0 项，平局取较小索引。混合结果的 RGBA 已经等于盖住索引的调色板色时，留下那个索引。压平后的层可见且完全不透明，所以只靠层透明度产生的半透明不会留在格子里；alpha 不计入距离，一半不透明的单层会变成那一项的不透明色。没有 multiply / screen。不改工程的对照是 `preview --compare`：左是未量化 RGBA，右是 flatten 会写下的索引再按调色板着色，默认 `<stem>.compare.png`。要真的收成单层再用 `preview --output before.png`，然后 `layer flatten`，再 `preview --output after.png`。见 [#114](https://github.com/starcloud530/pixelforge-ai/issues/114)、[#110](https://github.com/starcloud530/pixelforge-ai/issues/110) 和 [#98](https://github.com/starcloud530/pixelforge-ai/issues/98)。

*A translucent stack flattens to the nearest palette index. The color preview, `export png`, and `frame_rgba` stay the unquantized straight-alpha blend and do not write cells. ASCII and `diff` still show the covering index until flatten. `layer flatten` snaps that blend with the `apply-png` rule: alpha below 128 is index 0, otherwise the nearest opaque entry by squared RGB, and a tie keeps the lower index. A cell whose RGBA already equals the covering index keeps that index. The result layer is visible and fully opaque, so translucency that came only from layer opacity is not stored. Alpha is not part of the distance, and a lone layer at opacity 128 becomes that entry's opaque color. There is no multiply or screen. Compare without writing the project: `preview --compare` puts that blend on the left and the palette color of the indices flatten would write on the right (default `<stem>.compare.png`). To store the single layer, use `preview --output before.png`, then `layer flatten`, then `preview --output after.png`. See [#114](https://github.com/starcloud530/pixelforge-ai/issues/114), [#110](https://github.com/starcloud530/pixelforge-ai/issues/110), and [#98](https://github.com/starcloud530/pixelforge-ai/issues/98).*

## Direction fill is not a natural gait

`direction set` / `apply` 只按行写下已有的 idle/walk 标签区间，不画像素。`direction fill` 把一个基本朝向（N/E/S/W）里已经有的 `{动作}_{朝向}` 帧段拷到其余基本朝向，或把 left 与 right 水平镜像。目标帧已经有墨或显式擦除时默认跳过，`--overwrite` 才盖掉。八向的对角行这一版不填。镜像和拷贝都不是新画、不是自然步态、不修高光，也不是 PixelLab 那种自动画四向。`direction validate` 退出码 0 只说明四向（或可选的八向）帧段齐、没有缺方向或缺关键帧。它不生成走路，不检查脚滑，也不判断动作好不好看。像素仍要自己画，或同姿复制后改差。见 [#108](https://github.com/starcloud530/pixelforge-ai/issues/108) 和 [#116](https://github.com/starcloud530/pixelforge-ai/issues/116)。

*Direction auto-naming and direction fill are not a natural gait and not an aesthetic pass. `direction set` / `apply` only writes the idle/walk tag spans for the stored rows and does not paint. `direction fill` copies one cardinal facing's `{action}_{facing}` frames onto the other cardinals, or horizontally mirrors left and right. A target frame that already holds ink or an explicit erase is skipped unless `--overwrite` is set. Eight-direction diagonal rows are not filled. A mirror or a copy is not new art, not a natural gait, does not repair highlights, and is not a PixelLab four-direction draw. Exit 0 from `direction validate` means the four cardinal facings, or the optional eight with diagonals, have their frame spans and that none are missing. It does not generate a walk, it does not check foot slide, and it does not judge the motion. Paint the pixels, or duplicate a pose and edit the diff. See [#108](https://github.com/starcloud530/pixelforge-ai/issues/108) and [#116](https://github.com/starcloud530/pixelforge-ai/issues/116).*

## Direction review does not grade the drawing

`direction review` 只读，不改工程。它按一个动作和 `--at` 或 `--column` 从八个朝向各取一帧。缺的槽留空，不复制别的方向。基准要靠 `--origin-x/--origin-y`、`--origin-part`、`--foot-y`、`--foot-anchor` 或 `--anchor`。没有就写「未提供」。包围盒中心不是原点，最低不透明像素不是脚底。`parts` 在没有可求值的曲线或约束时是静止姿势，不是该帧锚点。退出码 0 只说明没有结构问题、也没有超出 `--tolerance` 的对齐偏差。侧面变窄和包围盒变化是观察，不判错，也不说明画得好。求值走 `solve_constraints` 且 `apply` 为 false；约束解失败时该基准是「未提供」，不改用包围盒。对齐把图限制在原画布里，移出的格子会被裁掉，JSON 里的偏移仍是完整差值。

*`direction review` is read-only and does not change the project. It takes one frame of one action from each of eight facings, using `--at` or `--column`. An empty slot is not filled from another facing. A baseline comes from `--origin-x`/`--origin-y`, `--origin-part`, `--foot-y`, `--foot-anchor`, or `--anchor`. Otherwise the report says 未提供. The bounding-box center is not an origin, and the lowest opaque pixel is not a foot. Without an evaluable curve or constraint, `parts` is the rest pose, not that frame's anchor. Exit 0 means there is no structural finding and no alignment offset past `--tolerance`. A narrower side view and a changed bounding box are observations. They are not errors, and they do not mean the drawing looks good. Evaluation uses `solve_constraints` with `apply` false. A failed solve leaves that baseline as 未提供 and does not fall back to the bounding box. Alignment stays inside the original canvas, so shifted cells can clip, while the JSON offset keeps the full delta.*

## Project manifest is memory, not a canvas

`pixelforge project` 读写 `pixelforge-manifest`：尺寸档、视角、目录约定、默认色板路径、一段短说明、资产根和相对路径。`assets` 只保存你登记的稳定 id 和关系。像素仍在 `pixelforge-project`。`project validate` 或 `asset validate` 退出码 0 只说明约定、已登记的路径和关系对得上。它不扫描目录来发明 id，也不做导出清单，也不画像素。朝向 × 动作缺格是 `character matrix` / `character check`：对照 `directionLayout`、clip `tags` 和工程标签，报告 present / missing / empty / placeholder。矩阵绿 ≠ 步态或观感合格。可视化素材管理、地图 GUI、内嵌聊天、团队权限、自动生图都不在这里。见 [project-manifest](project-manifest.md)。

*A project manifest is project memory. `pixelforge project` reads and writes a `pixelforge-manifest`: canvas tiers, perspective, directory rules, the default palette path, a short note, and the asset root. `assets` stores only the stable ids and relations you register. Pixels stay in `pixelforge-project` files. Exit 0 from `project validate` or `asset validate` means those conventions, registered paths, and relations match. It does not scan a directory into new ids, it does not list an export, and it does not paint. Facing × action gaps are `character matrix` / `character check`. A green matrix is not a gait or an aesthetic pass. A visual asset manager, a map GUI, an embedded chat, team auth, and image generation are not this file. See [project-manifest](project-manifest.md).*

## Export / validate is not aesthetic QA

`export` 写出文件、`validate-atlas` 退出码 0、或 `the pack validate script in pixelforge-demos (when published)` 通过，只说明清单里没有 error。warning 仍可能在。剪影、头身、色阶、动作好不好看不在这份清单里。Godot / Unity 的过滤、轴心和 `idle_*` / `walk_*` 仍要在引擎里接。`export apng` 是可循环播放的预览，不是引擎用的 sprite sheet，`validate-atlas` 不读它。像素和 PNG 导出是同一份直通 RGBA，不把调色板收成 GIF 的索引色，也不抖动；调色板 alpha 和 1 到 254 的层透明度都留着。时长按毫秒写入（分母 1000），不收成百分之一秒。见 [export](export.md) 和 [[pixelforge-demos](https://github.com/starcloud530/pixelforge-demos) FAILURES notes (when published)](https://github.com/starcloud530/pixelforge-ai/blob/main/[pixelforge-demos](https://github.com/starcloud530/pixelforge-demos) FAILURES notes (when published))。

*`export` writes the files. Exit 0 from `validate-atlas`, and a pass from `the pack validate script in pixelforge-demos (when published)`, mean the checklist has no error. Warnings may remain. Silhouette, proportion, palette, and motion are outside that checklist. Filter, pivot, and `idle_*` / `walk_*` are still wired in Godot or Unity. `export apng` is a looping preview, not the engine sprite sheet, and `validate-atlas` does not read it. The pixels are the same straight RGBA as PNG export: no GIF palette quantization and no dither, so palette alpha and opacity 1..=254 stay. Delays are stored in milliseconds (denominator 1000), not centiseconds. See [export](export.md) and [[pixelforge-demos](https://github.com/starcloud530/pixelforge-demos) FAILURES notes (when published)](https://github.com/starcloud530/pixelforge-ai/blob/main/[pixelforge-demos](https://github.com/starcloud530/pixelforge-demos) FAILURES notes (when published)).*

## PNG convert is a sampler, not a quality score

`convert` 把一张 PNG 收成一帧索引色。源图每边最大 4096，目标边长仍是 `1..=256`。alpha 小于 128 写成索引 0，半透明不留在格子里。不透明格只取源图里已有的颜色，再按 `apply-png` 的平方 RGB 距离收成索引。五个开源引擎是 `center-sample`、`dominant`、`kmeans`、`contrast-outline`、`grid-snap`，同一输入和同一参数输出一致。`grid-snap` 找不到边缘时仍返回这一张图，`report.detected` 为 false，并改用中心采样；这不是换成另一个引擎。`pixelforge-native` 选中就报 `EngineUnavailable`，不回退，也不下载。`features` 只写进 `transform` 快照，这一版不使用。`palette.strategy` 有三个 id：`source` 沿用原图色板（快照 `mode` 是 `keep`；超过 255 个不透明色就拒绝），`limit` 把颜色收到 `maxColors`（快照 `mode` 是 `limit`，不是 `source`），`project` 映射到已经选过的工程色板。内置默认色板，包括 `--output` 新建的那份，是 `PaletteDefault`。别的帧或层还有墨水时，`source` 和 `limit` 是 `PaletteInUse`，不改那些格子。`paletteReport.frames` 列出每一个改过索引的帧。未知 id 不回退。没写策略时，`--output` 仍用 `mode: source` 把采样色封顶，并且没有 `paletteReport`。不抖动，也不打质量分；质量基准是 [#127](https://github.com/starcloud530/pixelforge-ai/issues/127)。放大不补细节。图块集只能转成和图块一样大。命令见 [tool-api](tool-api.md) 的 `convertPng`。

*`convert` writes one indexed frame from a PNG. A source edge above 4096 is refused. The target stays inside `1..=256`. Alpha below 128 becomes index 0, so partial alpha is not stored. Opaque samples stay colors that already exist in the source, then the `apply-png` nearest index is written. The five open-source engines are `center-sample`, `dominant`, `kmeans`, `contrast-outline`, and `grid-snap`. The same input and the same parameters write the same indices. When `grid-snap` finds no edge it still returns that image, with `report.detected` false, using center sampling; that is not a switch to another engine. `pixelforge-native` returns `EngineUnavailable` and does not fall back or download. `features` are stored on the `transform` snapshot and are not applied. `palette.strategy` is `source` (keep the image palette; the snapshot mode is `keep`; more than 255 opaque colors is refused), `limit` (cap at `maxColors`; the snapshot mode is `limit`, not `source`), or `project` (a palette this project already chose). The built-in default palette, including a new `--output` file, is `PaletteDefault`. When another frame or layer still has ink, `source` and `limit` are `PaletteInUse` and do not change those cells. `paletteReport.frames` lists every frame whose indices changed. An unknown id does not fall back. Without a strategy, `--output` still caps sampled colors with `mode: source` and does not emit `paletteReport`. There is no dither and no quality score. The quality benchmark is [#127](https://github.com/starcloud530/pixelforge-ai/issues/127). Upscaling does not invent detail. A tileset converts only at the tile size. Commands: `convertPng` in [tool-api](tool-api.md).*
